# Phase 7F — Google Customer Identity Plan

Target commit chain on top of `phase5-booking-hold-guest-access` from
HEAD `3f559edbef9ab0161aa8d41fcac63dd2e734266f`. Expected schema evolves from
`phase-7e-dual-provider-delivery-v1` → `phase-7f-google-customer-identity-v1`.

## A. Schema changes (one forward-only migration)

New Drizzle migration `0012_phase7f_google_customer_identity.sql`:

1. Extend `bookings` with `customer_user_id UUID NULL`.
   - FK `bookings.customer_user_id -> users.id` (`ON DELETE RESTRICT`).
   - Index `bookings_customer_user_id_created_idx (customer_user_id, created_at DESC)` partial
     `WHERE customer_user_id IS NOT NULL`.
   - All existing rows keep `customer_user_id = NULL` (no backfill from email).
2. New table `customer_profiles`:
   - `user_id UUID PRIMARY KEY` FK to `users.id` (`ON DELETE RESTRICT`).
   - `normalized_phone_e164 TEXT NULL` (≤32 chars, E.164-ish regex).
   - `address_line_1`, `address_line_2`, `ward`, `district`, `province`, `postal_code`
     TEXT NULL each (trimmed, ≤200 chars).
   - `country_code TEXT NOT NULL DEFAULT 'VN'` (`CHAR(2)`-style regex check).
   - `created_at`, `updated_at TIMESTAMPTZ`.
   - Check constraints mirror the rules above.
3. Update `schema_metadata` to `phase-7f-google-customer-identity-v1`.
4. Update Drizzle snapshot (`meta/0012_snapshot.json`) — regenerated by `pnpm db:generate`.

`users`, `sessions`, `accounts`, `verification_records` tables stay as-is — Better
Auth continues to manage them. Roles remain `ADMIN` / `CUSTOMER`. No password
columns on `users`; password storage lives only inside `accounts` (Better Auth
account row).

## B. Google configuration (server-side only)

Add to `@room/config` (extends `apiEnvironmentSchema`):

- `GOOGLE_AUTH_ENABLED` (boolean; default `false`).
- `GOOGLE_CLIENT_ID` (string, optional unless enabled).
- `GOOGLE_CLIENT_SECRET` (string ≥16 chars, optional unless enabled).
- `GOOGLE_REDIRECT_URI` (URL string, optional unless enabled).
- `GOOGLE_AUTH_BASE_URL` (URL, optional; defaults to `AUTH_BASE_URL`).

Validation:

- When `GOOGLE_AUTH_ENABLED=false`: credentials may be empty; missing keys allowed.
- When `GOOGLE_AUTH_ENABLED=true`: `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`,
  `GOOGLE_REDIRECT_URI` are required.
- Production:
  - `GOOGLE_REDIRECT_URI.protocol === 'https:'` (loopback rejected).
  - `GOOGLE_CLIENT_SECRET` may not contain `test-` or `placeholder`.
  - `GOOGLE_CLIENT_ID` may not equal `placeholder-client-id` or `test-client-id`.
- Test (`NODE_ENV='test'`):
  - HTTPS not required; loopback `http://localhost` or `http://127.0.0.1` allowed.
- Errors include variable names only, never values.

Add `@room/config` unit tests covering: disabled, missing creds, bad URL,
production HTTP, production loopback, placeholder, valid test loopback,
valid production-shaped config.

`.env.example` documents variable names only.

## C. Better Auth factory extension

`packages/auth/src/auth-factory.ts` accepts additional `googleAuth` block.
New helper file `packages/auth/src/google-auth.ts`:

```ts
export interface GoogleAuthEnvironment {
  readonly enabled: boolean;
  readonly clientId?: string;
  readonly clientSecret?: string;
  readonly redirectUri?: string;
}
export function buildGoogleSocialProvider(env: GoogleAuthEnvironment) {
  if (!env.enabled) return {};
  return {
    socialProviders: {
      google: {
        clientId: env.clientId!,
        clientSecret: env.clientSecret!,
        redirectURI: env.redirectUri!,
        // default scopes: email, profile, openid (Better Auth default)
        mapProfileToUser: () => ({ role: 'CUSTOMER' }),
      },
    },
    user: {
      additionalFields: {
        role: { type: 'string', required: false, defaultValue: 'CUSTOMER', input: false },
        status: { type: 'string', required: false, defaultValue: 'ACTIVE', input: false },
      },
    },
    account: {
      accountLinking: { enabled: false, disableImplicitLinking: true },
    },
  };
}
```

`createRoomAuth` now accepts optional `googleAuth` and merges the
`socialProviders` / `user.additionalFields` / `account` blocks. The
`apiEnvironment` is still loaded once at startup via `requireApiEnvironment`
and passed to `createRoomAuth` from `app.module.ts`.

Role safety:

- `mapProfileToUser` on Google provider only ever returns `role: 'CUSTOMER'`.
- `additionalFields.role` has `input: false` so the API and Web cannot override.
- Default `status: 'ACTIVE'` (Better Auth also enforces via `DISABLED` checks).
- `accountLinking.enabled = false` and `disableImplicitLinking = true` ensure
  no silent account merge by email.
- ADMIN bootstrap path is unchanged — only `bootstrap-admin.ts` creates ADMINs.

Better Auth callback URLs are owned entirely by the library; the API does not
build OAuth URLs by hand. `sign-in/social` endpoint is wired through
`/api/auth/sign-in/social` (auto by Better Auth + the existing fastify bridge).

Disabled users: Better Auth's `internalAdapter` rejects sessions when
`user.status !== 'ACTIVE'`. We add a `databaseHooks.session.create.before` hook
that returns `false` when the user is `DISABLED`, ensuring `createSession` is
aborted.

Image rendering: `image` field is treated as untrusted URL; Web renders it via
a `<img>` with `referrerPolicy="no-referrer"` and `loading="lazy"`. No
`dangerouslySetInnerHTML`.

## D. CUSTOMER profile model

New table `customer_profiles` (see A). API surface:

- `GET /api/v1/customer/profile`
- `PATCH /api/v1/customer/profile`
- `GET /api/v1/customer/bookings` (paginated)
- `GET /api/v1/customer/bookings/:bookingCode`
- `POST /api/v1/customer/bookings/:bookingCode/claim`

All require:

- authenticated session (Better Auth session cookie)
- actor.role === 'CUSTOMER' (ADMINs are rejected here)
- user.status === 'ACTIVE'
- no browser-supplied user id

PATCH body schema (Zod, server-side validated):

- name: 1..120 chars
- phone: E.164 (optional, empty → null)
- addressLine1, addressLine2, ward, district, province, postalCode: each
  trimmed; empty → null; ≤200 chars
- countryCode: `^[A-Z]{2}$` (default `VN`)
- email: NOT accepted (rejected with `READ_ONLY_LOGIN_EMAIL`)

Audit payload contains:

- actorId, eventType=`CUSTOMER_PROFILE_UPDATED`, changed field names only,
  correlationId, requestId. No phone, address, or email.

## E. Authenticated booking ownership

`BookingHoldService` gains an optional `customerUserId`. When present and the
actor is a CUSTOMER, `insertBooking` writes `customer_user_id`. Browser never
supplies it.

`BookingHoldController` reads an injected `CustomerSessionReader` (which
re-uses `AdminSessionService`-style Better Auth `getSession` + role check).
If no CUSTOMER session, no `customer_user_id`. If session exists but actor is
ADMIN or DISABLED, request is denied with `CUSTOMER_SESSION_REQUIRED`.

`createBookingHoldWithRetry` keeps guest path identical; new `customerUserId`
parameter is the only addition. No migration of existing bookings.

## F. Guest booking claim transaction

`ClaimBookingService`:

1. Read CUSTOMER session (must be ACTIVE CUSTOMER).
2. Read guest session cookie (`rm_guest_session_v1`); verify it is bound to
   exactly the booking code in path.
3. Begin DB transaction, `SELECT … FOR UPDATE` on booking row.
4. If `booking.customer_user_id IS NULL`, set it to current CUSTOMER user id.
5. If already equals current id → idempotent success.
6. If different → return 409 `BOOKING_ALREADY_LINKED`.
7. Insert `audit_events` row: `aggregateType='BOOKING'`, `eventType='BOOKING_CLAIMED'`,
   `actorType='CUSTOMER'`, `actorId=<userId>`, payload includes only
   `bookingId`, `bookingCode`, `requestId` — no email, phone, or other PII.
8. Commit.

Route: `POST /api/v1/customer/bookings/:bookingCode/claim` requires an active
guest session cookie (binding to that exact booking). When a verified
booking-scoped guest session exists, the claim is allowed.

Optional supporting evidence: when CUSTOMER's `users.email` matches the
booking contact's `normalizedEmail` digest, write a `supportingMatch: true`
flag into the audit payload; but the proof of ownership is still the guest
session. **Email text alone never claims a booking.**

## G. CUSTOMER booking APIs

`GET /api/v1/customer/bookings?limit=20&cursor=<bookingId>`:

- Requires CUSTOMER session.
- SQL filter: `WHERE customer_user_id = $1`.
- Stable ORDER BY `(created_at DESC, id DESC)`.
- Cursor pagination using `(created_at, id)` pair; opaque cursor.
- Response: list of safe booking summary records.

`GET /api/v1/customer/bookings/:bookingCode`:

- Requires CUSTOMER session.
- SQL: `WHERE booking_code = $1 AND customer_user_id = $2`.
- Returns `BookingDetailResponse` (existing schema, only safe fields),
  augmented with `paymentStatus` from the existing
  `authoritative-payment-status` view (no internal ids, no provider attempts).

## I. Session and cookie security

Existing Better Auth cookie config stays. We add to `auth-factory.ts`:

- `advanced.cookieOptions` re-stated: HttpOnly, SameSite=Lax, Secure in production.
- `useSecureCookies: NODE_ENV === 'production'`.
- `trustedOrigins: [WEB_ORIGIN]`.
- `disabled-user` short-circuit in `databaseHooks.session.create.before`.

CSRF: Better Auth `sign-in/social` and `sign-out` endpoints rely on
`origin`/`referer` checks already provided by the library. We add
`onRequest` CORS handling so state-changing calls must be from `WEB_ORIGIN`.

## N. Self-review (security/correctness)

- ✅ Auto-linking by email: disabled (`accountLinking.enabled = false`).
- ✅ ADMIN privilege escalation via Google: impossible
  (`mapProfileToUser` returns `CUSTOMER` only; `additionalFields.role.input=false`).
- ✅ Phone assumption: never; profile PATCH owns it.
- ✅ Local password scope creep: no local-password UI, no forgot-password.
- ✅ Secret leakage: client secret server-only, no API exposure, no OpenAPI
  emission, no log emission.
- ✅ Account takeover: token replay impossible (Better Auth state+nonce+PKCE).
- ✅ Duplicate account race: `accounts_provider_account_uq` unique index
  guarantees one row per `(provider, accountId)`.
- ✅ Booking-claim race: `FOR UPDATE` lock on booking row inside
  transaction.
- ✅ OAuth open redirect: callback uses Better Auth state validation,
  `trustedOrigins` list, and `WEB_ORIGIN`-pinned CORS.
- ✅ Disabled-user behaviour: session creation aborted by hook + actor
  check in profile/booking/claim controllers.
- ✅ Test bypass leaks: only under `NODE_ENV='test'`; production build
  excludes `test-oauth-provider.ts` via explicit Vitest include patterns
  AND a runtime guard in the file (`if (process.env.NODE_ENV !== 'test') throw`).
