## Explicit non-negotiables

1. One stay is one booking.
2. One booking has one physical room for the complete `[checkInAt, checkOutAt)` interval.
3. The best candidate is fully valid first, operationally convenient second, and cheapest third.

The B0 execution order is: public interval input -> server policy validation
-> exact pricing eligibility -> complete-interval room-type availability ->
immutable quote -> transactional HOLD revalidation -> exactly one physical
room allocation -> one booking -> one inventory block -> one payment aggregate
-> lifecycle. Pricing and availability may be evaluated in either internal
order where the repository requires it, but both must pass before quote
issuance. No physical room is reserved before HOLD.

`overnight` remains the existing fixed one-night preset. The additive
multi-night intent is `multi_night`; in the current B0 release candidate it is
implemented behind server-side catalog, internal, and public gates that default
to false and fail closed. Production enablement remains a later approved step.

No customer request above authorizes client pricing, a frontend-only workaround, public physical-room identity, or repricing an accepted booking.
