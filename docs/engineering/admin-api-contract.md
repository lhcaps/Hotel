# Admin API contract

All operations are under `/api/v1/admin` and require a server-derived ADMIN session plus permission metadata. `/me` returns only id, email, display name, role, permissions, and session expiry. Catalog mutations use shared `@room/contracts` Zod schemas.

Errors use `application/problem+json` with `type`, `title`, `status`, `code`, `detail`, `requestId`, and field errors. Unknown errors never return PostgreSQL, credential, token, or session details. The committed OpenAPI artifact is generated by `pnpm generate:openapi` and checked by `pnpm check:openapi`.

Phase 4 adds `GET /rate-plans`, `PUT|PATCH /rate-plans/:id/prices/:priceTierId`, and activate/inactivate operations. They require pricing read/manage permissions, update integer-VND prices transactionally with scrubbed audit events, and refuse activation until every tier used by an active room type has a positive price. Public unauthenticated endpoints are separate: `POST /api/v1/availability/search`, `POST /api/v1/quotes`, and `GET /api/v1/quotes/:id`; their schemas never accept a client amount or expose physical-room identity.

## Phase 7G - Admin booking lifecycle

Phase 7G exposes the ADMIN booking-operations vertical under
`/api/v1/admin`. All routes require an active `ADMIN` session plus
the corresponding permission (`booking.lifecycle.*` or
`booking.review.*`).

### Bookings

| Method | Path                                            | Permission                 | Body                 | 2xx |
| ------ | ----------------------------------------------- | -------------------------- | -------------------- | --- |
| `GET`  | `/api/v1/admin/bookings`                        | `booking.lifecycle.read`   | n/a                  | 200 |
| `GET`  | `/api/v1/admin/bookings/:bookingCode`           | `booking.lifecycle.read`   | n/a                  | 200 |
| `POST` | `/api/v1/admin/bookings/:bookingCode/cancel`    | `booking.lifecycle.manage` | `{ reason: string }` | 200 |
| `POST` | `/api/v1/admin/bookings/:bookingCode/check-in`  | `booking.lifecycle.manage` | n/a                  | 200 |
| `POST` | `/api/v1/admin/bookings/:bookingCode/check-out` | `booking.lifecycle.manage` | n/a                  | 200 |
| `POST` | `/api/v1/admin/bookings/:bookingCode/no-show`   | `booking.lifecycle.manage` | `{ reason: string }` | 200 |

The booking list accepts `page`, `pageSize`, `q` (booking code),
`status`, `paymentStatus`, `roomTypeId`, `checkInFrom`, `checkInTo`,
and `reviewPresence` (`HAS_OPEN_REVIEW` | `NONE`). Pagination is
bounded and stable.

The booking detail returns: booking code, status, contact snapshot,
occupancy, room type, assigned physical room, interval, pricing
snapshot, coupon summary, safe payment summary, operational-review
state, transition timeline, and server-authoritative available
actions. Provider secrets, raw provider payloads, session tokens,
OTP digests, guest-session digests, stack traces, and SQL details are
never returned.

### Operational reviews

| Method | Path                                                  | Permission              | Body               | 2xx |
| ------ | ----------------------------------------------------- | ----------------------- | ------------------ | --- |
| `GET`  | `/api/v1/admin/operational-reviews`                   | `booking.review.read`   | n/a                | 200 |
| `GET`  | `/api/v1/admin/operational-reviews/:reviewId`         | `booking.review.read`   | n/a                | 200 |
| `POST` | `/api/v1/admin/operational-reviews/:reviewId/resolve` | `booking.review.manage` | `{ note: string }` | 200 |

The review list accepts `page`, `pageSize`, `status`, and `q`. The
review detail returns: review id, category, status, openedAt,
openedReason, resolvedAt, resolverId, resolvedNote, and the related
booking / payment summary. Resolution requires a non-empty note; it
writes `resolved_at`, `resolver_id`, and `resolved_note`, and never
modifies the booking, payment, coupon, or provider-event history.

### Operational review categories (Phase 8C)

Operational reviews may carry any of the following category values.
Each is opened automatically by the settlement or reconciliation core
and resolved manually through the `resolve` endpoint above.

| Category                              | Source   | Meaning                                                                             |
| ------------------------------------- | -------- | ----------------------------------------------------------------------------------- |
| `PAID_CANCELLATION`                   | Phase 7G | A verified success arrives after ADMIN cancellation.                                |
| `BOOKING_EXPIRED`                     | Phase 7C | A verified success arrives after HOLD expiry.                                       |
| `COUPON_RELEASED`                     | Phase 7C | A verified success arrives after coupon release.                                    |
| `INVENTORY_RELEASED`                  | Phase 7C | A verified success arrives after inventory release.                                 |
| `AMOUNT_MISMATCH`                     | Phase 7C | A verified success has a different amount.                                          |
| `TRANSACTION_CONFLICT`                | Phase 7C | A duplicate provider transaction id.                                                |
| `CROSS_PROVIDER_TRANSACTION_CONFLICT` | Phase 8C | Two providers attempted to settle the same booking; one was downgraded.             |
| `RECONCILIATION_EXHAUSTED`            | Phase 8C | Reconciliation cycle exhausted attempts; manual resolution required.                |
| `RECONCILIATION_TRANSIENT`            | Phase 8C | Reconciliation cycle observed a transient failure requiring ADMIN attention (rare). |
| `RECONCILIATION_NOT_FOUND`            | Phase 8C | Reconciliation cycle reports the order is unknown after grace.                      |
| `RECONCILIATION_STALE_FAILURE`        | Phase 8C | Reconciliation cycle reports provider failure but attempt was already settled.      |

The list and detail endpoints accept a `category` filter (single
value or comma-separated list) and return the count grouped by
category in the `categoryCounts` field on the list response.

### Coupon delivery request (Phase 8D)

| Method | Path                                               | Permission                                  | Body                                | Header                      | 2xx |
| ------ | -------------------------------------------------- | ------------------------------------------- | ----------------------------------- | --------------------------- | --- |
| `POST` | `/api/v1/admin/bookings/:bookingCode/send-coupons` | `booking.lifecycle.manage`, `coupon.manage` | `{ couponCodes: string[] }` (1..10) | `Idempotency-Key` (16..128) | 201 |

The mutation queues a transactional-outbox email request only. Its recipient is derived from the immutable booking contact snapshot; callers cannot supply an email. It returns `{ deliveryId, status }`, writes a count-only audit event, and does not reserve, redeem, or otherwise mutate a coupon lifecycle.

### Error mapping

- `BookingTransitionError` → 409 (illegal transition).
- `NoShowBeforeCheckInError` → 422 (no-show called before expected
  check-in).
- `OperationalReviewNotFoundError` → 404.
- `OperationalReviewAlreadyResolvedError` → 409.
- Missing / disabled ADMIN → 401 / 403.
- Missing permission → 403.
- Validation failure → 400 with problem-details.
